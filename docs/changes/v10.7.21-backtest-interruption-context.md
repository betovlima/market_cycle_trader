# Frontend v10.7.21 — contexto correto de backtests interrompidos

## Incidente observado

Em 2026-10-12, após executar os endpoints de cadastro e backtest do
Challenger U67+10, o Backtest local exibiu "Interrompido", 10,2% de progresso,
e um cabeçalho com Strategy #13 / U67 original.

## Causa da informação incorreta na interface

A página usava a estratégia atualmente selecionada no Dashboard quando o
job deixava de estar "running". Portanto, no estado "interrupted" o cabeçalho
podia exibir a Strategy selecionada no momento em vez da Strategy associada
ao job interrompido. Isso **não prova** que a execução foi do U67; a identidade
correta vem de `job.strategy_profile_id` e
`job.strategy_profile_name`.

O painel de andamento também não exibia o ID do job e o motivo de interrupção.

## Correção

- O cabeçalho usa a identidade do próprio job em `queued`, `running`,
  `failed`, `interrupted` e `cancelled`.
- O painel de progresso mostra ID do job e nome da Strategy correspondente.
- O modelo do job tem precedência sobre o modelo salvo atualmente.
- O campo `interruption_reason` recebido da API é apresentado explicitamente.
- O fluxo de criação de backtest, seleção, Candidate e Winner não foi alterado.
- Nenhuma trava ou validação extra foi introduzida.

## Diagnóstico do backend relacionado

O serviço API marca jobs `queued`/`running` como `interrupted` ao
reinicializar (`core/runtime.py`). A API foi adaptada para retornar esse
motivo explicitamente, preservando os dados do job.

Para backtests demorados na máquina local, usar Uvicorn **sem `--reload`**
durante a execução; salvar arquivo de código com hot reload pode reiniciar a
API e interromper o acompanhamento do job.

## Validação

Frontend v10.7.21. Confirmar build da branch e integração com a API atualizada.
Esta alteração melhora o diagnóstico, mas não implementa retomada automática
de jobs após reinício da API.
